# 第3章 系统总体设计

本章在前文需求分析和技术可行性分析的基础上，对基于用户行为分析的实时信息流排序与分发系统进行总体设计。系统总体设计主要包括体系架构设计、功能模块设计、数据库设计、推荐算法设计、接口与数据交互约定、关键术语说明以及实现系统所涉及的关键技术。与第四章的详细实现不同，本章重点说明系统各组成部分之间的关系、数据如何流转、推荐排序如何形成，以及各模块在整体架构中的定位。

## 3.1 系统体系架构设计

系统采用 B/S 架构，并使用前后端分离的开发模式。浏览器端运行 Vue 3 单页应用，主要负责页面展示、用户操作、状态维护和图表渲染等工作；后端使用 Spring Boot 提供 RESTful API 和 WebSocket 服务，用来处理系统中的业务逻辑、推荐排序和实时通信；数据库采用 MySQL 存储用户、内容、行为、标签、关注、通知、私信、广告和负反馈等业务数据；AI 服务主要通过本地 Ollama 模型接入内容打标和 AI 推荐辅助能力；外部数据导入模块用于导入公开数据集或补充种子内容，从而丰富系统候选内容池。

前后端分离能够使界面开发和算法调整相对独立。前端主要关注页面交互、信息流展示、用户画像展示和统计图表渲染，后端主要关注业务处理、数据一致性、推荐计算和接口响应。系统推荐链路在逻辑上可以分为数据层、特征层、排序层和展示层：数据层负责保存内容、行为和社交关系；特征层负责用户画像、标签偏好和文本向量等特征处理；排序层负责传统混合推荐或 AI 推荐策略的计算；展示层负责将普通内容、推荐解释和广告内容呈现给用户。

图3-1 系统总体架构图

后端采用分层设计，以提高代码可维护性和功能扩展性。controller 层作为请求入口，负责接收前端请求并调用对应业务方法；service 层承载主要业务逻辑，例如内容发布、行为统计、用户画像生成、推荐评分计算和广告分发等；repository 层负责与数据库交互，完成实体数据的增删改查；model 层定义 JPA 实体类，将数据库表映射为 Java 对象；dto 层封装前后端传输对象，避免直接暴露实体字段；config 层集中管理跨域、安全、WebSocket、文件访问映射和 AI 服务参数等配置。

推荐系统相关逻辑主要集中在 service 层。传统推荐策略、AI 推荐策略、策略管理器、用户画像服务、TF-IDF 服务和协同过滤服务分别承担不同职责，使候选池构建、特征计算、排序策略和异常降级能够相互分离。前端使用 DTO 对象接收后端返回结果，例如 ContentDTO 用于信息流展示，ScoreBreakdown 用于展示推荐评分明细，PersonaResponse 用于展示用户画像结果。通过这种数据结构约定，前端不需要额外拼接复杂字段，后端接口也能保持较清晰的输出边界。

## 3.2 功能模块设计

系统功能按照业务职责划分为用户认证与资料、内容发布与互动、社交关系、行为采集、推荐排序、用户画像、搜索与热门话题、通知与私信、广告分发、AI 智能、管理后台和数据导入等模块。各模块并不是相互孤立运行，而是通过 REST API、WebSocket 推送和共用数据库表进行协同，共同支撑系统的主要业务流程。系统核心功能模块结构如图 3-2 所示。

图3-2 系统核心功能模块结构图

在系统运行过程中，前端页面通过统一接口调用后端服务，后端根据不同业务类型调用对应的 service 和 repository，从而保证页面交互、业务处理和数据存储之间保持清晰的分层关系。普通用户侧主要围绕注册登录、信息流浏览、内容发布、点赞评论、转发引用、关注、搜索、通知和私信等功能展开；管理员侧主要负责推荐策略切换、用户状态管理、广告配置、统计分析和外部数据导入等工作，使系统既能面向普通用户提供信息流服务，也能面向管理员提供运行维护入口。

用户认证与资料模块负责用户注册、登录、角色识别和资料维护。注册时系统需要校验用户名唯一性，登录时需要校验账号状态和登录凭证，并返回用户信息与 Token。当前系统通过 JWT 令牌识别用户身份，前端保存登录状态后，在访问受保护页面或接口时携带身份信息。管理员入口则结合角色字段进行区分，使后台管理功能与普通用户功能保持边界。

内容发布与互动模块负责帖子、评论、转发、引用和图片上传等内容生产行为。用户可以发布文字或图片内容，也可以对已有帖子进行点赞、点踩、评论、转发和引用。系统在保存内容时会解析正文中的话题标签，并在必要时调用 AI 打标能力补充语义标签。互动行为既会影响内容本身的统计字段，也会作为用户画像和推荐排序的重要输入。

社交关系模块主要维护用户之间的关注关系。关注关系一方面支撑用户主页、关注列表和粉丝列表展示，另一方面也为推荐排序提供 In-Network 候选内容来源。当前用户关注对象发布的内容可以进入关注流，也可以在 For You 推荐流中获得一定的社交来源加成。

行为采集模块为用户画像和推荐排序提供基础数据。系统会记录浏览、点赞、评论、转发、搜索、点踩、跳过等行为，并根据行为类型和发生时间判断用户兴趣强度。浏览行为可以结合停留时长分析浅阅读或深度阅读倾向；搜索行为能够体现用户主动检索意图；点踩、不感兴趣、屏蔽和静音等负反馈则用于候选过滤或排序惩罚。

推荐排序模块是系统的信息流分发核心。系统根据用户 ID、分页参数、关注关系、历史行为和负反馈记录构建候选池，再调用当前启用的推荐策略进行打分、排序和重排。传统混合推荐策略综合考虑互动质量、标签匹配、TF-IDF 文本相似度、协同过滤、热门话题、时间衰减、作者偏好和随机探索等因素；AI 推荐策略则在候选内容基础上调用大语言模型进行语义辅助排序和推荐理由生成。

用户画像模块根据用户行为记录、内容标签、作者信息和行为时间窗口生成兴趣画像。画像结果包括兴趣标签分布、作者偏好、互动风格、内容深度偏好、新鲜度偏好和用户阶段等信息，并输出动态权重 DynamicWeights，为推荐排序和广告匹配提供个性化参数。对于冷启动用户，系统会使用全局热门、新鲜内容和随机探索等方式进行兜底。

搜索与热门话题模块用于补充用户主动兴趣和全站内容热度信号。搜索接口返回帖子、用户和话题等结果，同时可记录 SEARCH 类型行为；热门话题统计则根据内容数量和互动量聚合全站标签热度，为推荐排序中的热门话题加成和统计页面展示提供依据。

通知与私信模块负责互动事件和点对点消息的送达。点赞、评论、关注、转发和引用等行为可以触发通知生成，私信功能则保存用户之间的聊天记录。系统先将通知或消息写入数据库，再通过 WebSocket 向在线用户推送；当用户离线或连接异常时，数据库记录仍然保留，用户再次进入系统后可通过列表接口补偿查看。

广告分发模块负责信息流广告插入、广告配置管理和展示点击统计。系统根据广告定向标签、用户画像标签、广告出价和历史点击率计算广告匹配分，并按照配置间隔将广告卡片插入信息流。广告模块和推荐模块都使用用户画像数据，但二者目标不同：推荐模块更关注内容相关性和信息流多样性，广告模块更关注标签匹配、点击率和投放效果，因此广告排序与普通内容推荐保持相对独立。

AI 智能模块主要用于内容自动打标、AI 推荐辅助和智能问答等功能。内容自动打标可以为缺少标签的帖子补充语义信息，AI 推荐可以对候选内容进行语义层面的辅助重排并生成推荐理由。考虑到本地模型可能出现响应慢或格式不稳定的情况，系统为 AI 调用设置了超时、缓存和降级机制，确保 AI 功能异常时信息流主流程仍可使用。

管理后台和数据导入模块为系统运行维护提供入口。管理员可以在后台查看统计数据、切换推荐策略、管理用户状态、维护广告配置、触发 AI 打标和导入外部数据。数据导入模块主要用于补充公开数据集内容，并在外部数据不足时通过内置内容库补齐，从而降低演示和测试阶段候选内容不足带来的影响。

## 3.3 数据库设计

数据库设计围绕用户、内容、行为、社交关系、推荐辅助数据和广告数据等方面展开。系统中的核心实体包括用户、内容、行为、标签、关注、通知、私信、负反馈、广告和广告配置等。用户实体与内容实体之间存在一对多关系，一个用户可以发布多条内容；用户实体与行为实体之间也存在一对多关系，用户在浏览、点赞、评论、搜索等过程中会产生多条行为记录；用户之间通过关注关系形成有向社交关系，为关注流和推荐候选召回提供依据。

内容实体是系统信息流展示和推荐排序的核心数据对象。一条内容可以关联多个标签，也可以触发多条通知记录；在评论、转发和引用等场景下，内容还可以作为其他内容的目标对象。广告相关数据主要根据广告标签、广告类别、出价和历史展示点击效果参与信息流广告插入。表结构设计既要保证用户、内容、行为和标签等核心数据之间的关联关系清晰，也要兼顾推荐排序、画像统计和广告分析时的查询效率。因此，各数据表通常通过主键字段唯一标识记录，并通过用户 ID、内容 ID、标签 ID、行为类型和创建时间等字段建立查询条件。

## 3.4 推荐算法设计

推荐排序模块是系统实现个性化信息流分发的核心部分。系统在生成 For You 信息流时，不再单纯按照发布时间倒序展示内容，而是综合考虑用户行为、内容特征、社交关系、时间因素、负反馈和一定的随机探索机制，对候选内容进行综合排序。整体来看，推荐流程可以分为候选内容召回、候选过滤、特征计算、综合评分、重排调整和结果返回几个步骤。

### 3.4.1 推荐策略总体设计

推荐排序模块采用策略模式设计，后端统一定义推荐策略接口 RecommendationStrategy，传统混合推荐策略 HybridRecommendationStrategy 和 AI 推荐策略 AiRecommendationStrategy 均实现该接口。推荐策略管理器 RecommendationStrategyManager 负责保存不同推荐策略实例，并维护当前启用的策略标识，例如 traditional 和 ai。推荐服务 RecommendationService 在完成候选池组装后，将候选内容交给策略管理器，由当前启用的策略完成排序计算。

通过这种设计，业务代码不需要固定依赖某一种推荐算法，也方便后续进行策略切换和扩展。管理员可以通过后台接口切换推荐策略，切换完成后，用户的 For You 信息流请求会按照新的策略返回结果，从而便于观察传统推荐和 AI 推荐之间的输出差异。若后续需要新增其他推荐策略，只需要实现统一接口并注册到策略管理器中即可。

在整体流程上，系统首先根据当前用户 ID 获取用户关注关系、历史行为和画像信息；然后从关注用户发布内容和全站公开内容中召回候选帖子；接着结合负反馈记录对候选内容进行过滤；之后计算候选内容的多项评分特征，包括行为热度、标签匹配度、文本相似度、协同过滤加成、时间衰减、热门话题加成和作者偏好等；最后根据综合得分完成排序，并通过作者多样性、重复曝光惩罚和随机探索机制对列表进行调整，生成最终推荐结果。

### 3.4.2 候选内容召回与过滤

候选内容召回阶段采用双源候选机制，即将候选内容分为 In-Network 和 Out-of-Network 两类。In-Network 候选主要来自当前用户已关注用户发布的内容，用于保留社交关系带来的确定性内容来源；Out-of-Network 候选则来自全站公开内容池，用于帮助用户发现尚未关注但可能感兴趣的作者和话题。两类候选内容合并后，系统根据内容 ID 进行去重，形成统一候选列表。

在候选过滤阶段，系统结合负反馈信号表对候选内容进行处理。若用户对某一作者执行屏蔽或静音操作，则该作者发布的内容会在候选阶段被过滤；若用户对某一条内容标记“不感兴趣”，则该内容会被降低展示优先级或直接剔除。将负反馈过滤放在正式评分之前，可以避免无效内容继续参与 TF-IDF、协同过滤等后续计算，减少不必要的计算开销，也能提高推荐结果与用户真实偏好的匹配程度。

### 3.4.3 多因子评分模型

传统混合推荐策略是系统推荐排序的主要方法。系统会对每条候选内容计算多个评分分项，并将这些分项组合为最终推荐得分。主要评分项包括多行为加权互动分、标签匹配分、TF-IDF 内容相似度分、协同过滤加成、热门话题加成、时间衰减因子、作者偏好加成、内容深度匹配加成和新鲜度偏好加成等。

多行为加权互动分主要用于反映内容本身的互动质量。不同行为对用户兴趣的表达强度不同，一般来说，评论和转发比点赞更能体现用户兴趣，点赞又比普通浏览更能体现正向倾向。因此，系统根据行为类型设置不同权重，并结合点赞数、评论数、转发数和浏览数等统计字段计算内容互动得分。同时，为避免旧内容长期占据推荐列表，系统引入时间衰减因子，使发布时间较近的内容在相同互动条件下具有更高展示机会。

在文本相似度计算方面，系统采用 TF-IDF 方法表示内容文本特征。系统先对文本内容进行分词处理，然后计算词项 i 在文档 d 中的 TF-IDF 权重。结合项目中 TfIdfService 的实现，词项权重可表示为：

$$
w_{i,d}=tf(i,d)\times \left(\log \frac{N}{df(i)+1}+1\right)
\tag{3-1}
$$

式中，N 表示语料中的文档总数，df(i) 表示包含词项 i 的文档数量，tf(i,d) 表示词项 i 在文档 d 中出现的频率。通过这种方式，系统可以把文本内容转化为向量形式，再利用余弦相似度计算用户兴趣向量与候选内容向量之间的相近程度：

$$
sim(u,c)=\frac{V_u\cdot V_c}{\left|V_u\right|\times \left|V_c\right|}
\tag{3-2}
$$

式中，V_u 表示用户兴趣向量，V_c 表示候选内容向量。该相似度作为内容相似度加成（tfidfSimilarityBoost）的主要来源，用于刻画语义层面的兴趣匹配，从而弥补纯标签匹配粒度较粗的问题。

协同过滤加成主要根据用户之间的历史交互相似度进行计算。协同过滤服务 CollaborativeFilteringService 基于用户—内容交互矩阵，结合多行为权重和时间衰减计算用户相似度，产出相似用户及其偏好内容集合。如果候选帖子 ID 出现在协同推荐集合中，系统会给予该内容一定的协同过滤加成（collaborativeBoost）。该方法能够在标签较少或新话题刚出现时，利用其他用户的行为记录补充兴趣判断。

在完成上述评分项计算后，传统混合推荐策略进一步计算每条内容的最终推荐得分。由于评分项较多，式（3-3）采用缩写形式表示各个分项：

$$
finalScore=\frac{E}{D_t}+B_{tag}+B_{tfidf}+B_{cf}+B_{trend}+B_{author}+B_{depth}+B_{fresh}+\varepsilon
\tag{3-3}
$$

式中，E 表示多行为加权互动分，D_t 表示时间衰减因子，B_tag 表示标签匹配加成，B_tfidf 表示文本相似度加成，B_cf 表示协同过滤加成，B_trend 表示热门话题加成，B_author 表示作者偏好加成，B_depth 表示内容深度匹配加成，B_fresh 表示新鲜度偏好加成，ε 表示随机扰动项。各评分项会结合用户画像服务 UserBehaviorProfileService 输出的动态权重集合 DynamicWeights 进行组合计算，使不同用户在排序时体现不同的兴趣侧重点。

系统根据行为数量将用户划分为冷启动用户、初级用户和活跃用户。冷启动用户行为较少，推荐时更多依赖热门内容、新鲜内容和随机探索；初级用户已经积累部分行为，推荐策略采用热门内容与个性化内容混合；活跃用户行为数据较丰富，推荐时更多依赖个性化画像、协同过滤和作者偏好。用户阶段与推荐策略的关系如表 3-11 所示。

表 3-11 用户阶段与推荐策略

| 用户阶段 | 判定条件 | 推荐策略特点 |
| --- | --- | --- |
| 冷启动用户 | 行为数少于 10 | 更多依赖热门内容、新鲜内容和探索因子。 |
| 初级用户 | 行为数 10 到 49 | 热门内容与个性化标签匹配混合排序。 |
| 活跃用户 | 行为数不少于 50 | 更多依赖个性化画像、协同过滤和作者偏好。 |

### 3.4.4 重排与探索机制

在完成综合评分后，系统还会对初步排序结果进行重排调整。首先，系统会对用户已经产生过明显反馈的内容进行重复曝光惩罚。对于点踩过的内容，系统施加较强惩罚；对于点赞过或浏览过的内容，则适当降低其展示优先级。这样既可以减少用户明确不感兴趣内容的重复出现，也可以让更多新内容获得曝光机会。已点赞和已浏览内容并不会被系统完全屏蔽，而是通过降低分数的方式减少重复展示频率。

其次，系统加入作者多样性约束。若同一作者在候选列表中连续出现较多内容，系统会降低后续同作者内容的排序位置，避免推荐列表被单一作者占据。在具体处理时，可以沿推荐列表设置滑动窗口，统计同一作者在窗口中出现的次数；当次数超过阈值时，对后续同作者内容追加惩罚项或适当后移。该机制可以提高信息流内容来源的多样性，使用户看到的内容更加分散。

最后，系统引入一定的随机探索机制。若每次都直接返回得分最高的 Top-N 内容，推荐结果可能会过于固定，不利于发现用户的新兴趣。因此，系统可以在高分候选集合中加入随机扰动或加权随机采样，使部分分数略低但仍具有潜在价值的内容获得展示机会。加权随机采样可以根据候选内容得分构建权重分布，再按照权重概率选取内容，其思想可表示为：

$$
P(c_i)=\frac{score(c_i)}{\sum_j score(c_j)}
\tag{3-4}
$$

式中，P(c_i) 表示候选内容 c_i 被选中的概率，score(c_i) 表示候选内容的推荐得分。通过这种方式，系统可以在“利用高分内容”和“探索新内容”之间取得一定平衡。评分拆分对象 ScoreBreakdown 会把各个评分分项写入 DTO，前端页面可以展开查看这些分项，以增强推荐结果的可解释性。

### 3.4.5 AI 推荐与降级机制

除了传统混合推荐策略，系统还设计了 AI 推荐作为智能增强。这里的 AI 推荐并不是重新训练一个大规模推荐模型，而是在候选召回、负反馈过滤和基础排序完成之后，借助大语言模型对部分候选内容进行语义理解、辅助重排序并生成推荐理由。它不替代传统推荐管道，只是推荐排序链路中的增强策略，与传统混合推荐共同支撑信息流分发。

AI 推荐功能主要依赖本地部署的 Ollama 服务。后端在配置文件中设置模型服务地址、推荐模型名称、温度参数和最大输出长度，将本地大语言模型接入推荐流程。AI 调用、结果解析和异常处理均由后端统一完成，前端不直接参与模型推理。AiRecommendationStrategy 负责实现 AI 推荐策略，并通过统一的 RecommendationStrategy 接口与传统混合推荐策略保持一致的调用方式，方便管理员在后台切换策略并对比效果。

进入 AI 推荐流程后，系统先构建候选内容池，按基础互动分或传统推荐得分进行预排序，从中选取一部分候选内容输入模型，避免一次性传入过多内容。随后，系统整理当前用户的画像摘要和候选内容摘要。用户画像摘要主要包含用户阶段、兴趣话题、互动风格、内容深度偏好、新鲜度偏好和画像概括；候选内容摘要主要包含内容 id、正文片段、标签以及点赞数、评论数、转发数等互动统计。这些信息被组织成 Prompt，并要求模型按照固定 JSON 格式返回结果。

从推荐原理上看，AI 推荐主要利用大语言模型对文本语义和上下文的理解能力辅助判断候选帖子。传统混合推荐更多依赖标签匹配、TF-IDF 相似度、协同过滤和数值权重，AI 模型则能够进一步理解帖子正文中的主题、表达倾向和语义关联。对于标签较少、文本较短或单纯依靠关键词难以判断兴趣匹配程度的内容，AI 推荐可以作为传统混合排序的补充，让推荐结果在语义层面更贴近用户近期兴趣。

具体实现上，后端通过 HTTP 请求调用 Ollama 接口，请求内容包括模型名称、Prompt、是否流式输出和生成参数。为便于解析，系统将模型输出约束为 JSON 结构，返回结果主要包含 ranking 和 reasons 两类字段，其中 ranking 表示候选内容 id 的推荐顺序，reasons 存放对应内容的推荐理由。后端收到模型响应后，提取 JSON 内容并进行格式校验，判断 ranking 中的内容 id 是否存在于原候选集合中；对于无效 id 或重复 id，系统会进行过滤处理，对模型未覆盖但仍在候选池中的内容进行补齐，保证最终推荐列表完整可用。

考虑到本地大模型推理耗时较长，系统在设计中加入缓存和异步处理。AI 推荐模式下，如果缓存中已有当前用户可用的 AI 推荐结果，就直接返回缓存内容；缓存未命中时，系统优先返回传统混合推荐结果，同时在后台触发 AI 推荐计算，计算完成后更新缓存。通过这种方式，可以降低模型推理延迟对用户浏览体验的影响。

系统还设置了降级机制，以确保 AI 模块出现异常时主流程仍然可用。当 Ollama 服务不可用、请求超时、模型返回内容为空或返回的 JSON 格式不符合要求时，信息流请求不会被中断，而是回退到传统混合推荐策略；如果传统排序所需数据也不足，则按基础互动量对候选内容进行排序，并在评分说明或推荐理由中体现降级状态。通过这种处理，AI 推荐不会干扰系统基础推荐链路的稳定性。

### 3.4.6 推荐流水线与复杂度分析

一次 For You 请求的推荐流水线可以概括为身份解析、候选召回、负反馈过滤、画像读取、特征计算、排序重排、随机探索和分页返回几个阶段。首先，前端请求携带用户身份信息，后端解析出当前 userId；其次，系统从关注用户发布内容中获取 In-Network 候选，从全站公开内容中获取 Out-of-Network 候选，并按 contentId 去重形成候选集合 C。

候选集合生成后，系统读取负反馈记录，对被屏蔽作者、不感兴趣内容和静音作者进行过滤。若使用哈希集合保存负反馈目标，每条候选内容只需要一次快速判断，因此该阶段复杂度可近似看作 O(|C|)。随后，系统读取用户画像和协同过滤结果。用户画像聚合与用户历史行为数量 B 有关，若画像已经缓存或近期已计算，则推荐接口可直接读取结构化画像结果；协同过滤推荐列表也可以通过预计算或缓存降低实时计算成本。

在逐条评分阶段，系统为候选集合 C 中的每一条内容计算 ScoreBreakdown。若 TF-IDF 相似度采用向量点积计算，向量长度受词典维度 L 影响，则单条内容计算复杂度约为 O(L)，整体计算复杂度约为 O(|C|×L)。完成评分后，系统按 finalScore 排序，复杂度约为 O(|C|log|C|)。作者多样性控制和重复曝光惩罚通常可以借助哈希表或滑动窗口在线性时间内完成。

当系统启用 AI 推荐策略时，主要耗时来自模型推理和接口等待。为控制延迟，系统会先对候选内容进行截断，仅将一部分候选摘要输入模型；若模型调用失败或超时，则降级到传统混合推荐结果。综合来看，传统推荐路径的主要瓶颈在候选评分和排序，AI 推荐路径的主要瓶颈在模型推理。后续如果系统规模扩大，可以通过候选截断、向量缓存、倒排索引、画像预热和异步 AI 计算等方式继续优化。

### 3.4.7 本节小结

总体来看，本系统推荐算法并不是依赖单一排序规则，而是将用户行为画像、内容特征、社交关系、文本相似度、协同过滤、时间衰减、负反馈过滤和多样性控制等因素组合起来，形成适合毕业设计数据规模和演示需求的混合推荐方案。该方案在保证系统可运行、可解释和可调节的基础上，能够较好地体现个性化信息流推荐的基本思想。

## 3.7 实现系统的关键技术

本节从工程实现角度概括系统中使用的关键技术，重点说明这些技术在项目中通过什么机制落地、解决了哪些实现问题，以及与哪些类、接口和数据结构相关。与第二章的技术可行性分析不同，本节不再泛泛介绍技术名称，而是结合本系统的代码组织、数据处理和推荐链路说明具体实现方式。

### 3.7.1 前后端分离与分层后端实现

系统采用 Vue 3 + Spring Boot 的前后端分离模式。前端通过 Axios 调用后端 REST 接口，页面状态由路由、组件和本地会话共同维护；后端按照 controller、service、repository、model、dto 和 config 分层组织。controller 层只负责请求接收、参数校验和响应封装，核心业务逻辑下沉到 service 层，数据库访问通过 repository 层完成。这种分层方式可以避免控制器中堆积复杂业务逻辑，也便于在第四章按模块说明具体处理流程。

在数据传输方面，系统使用 DTO 隔离数据库实体与前端展示结构。例如内容实体 Content 中包含作者、正文、图片、父内容、转发来源和统计字段等信息，但前端信息流页面更需要 ContentDTO 中已经整理好的展示字段；推荐对比页面则需要 ScoreBreakdown 展示推荐得分分项。通过 DTO 封装，可以减少前端对数据库结构的依赖，也便于后续调整实体字段而不破坏页面渲染。

### 3.7.2 用户行为采集与画像建模技术

用户画像模块由行为数据驱动生成。系统读取用户历史行为记录后，查询相关内容和标签，并根据行为类型赋予不同权重。转发和评论通常代表较强兴趣，点赞代表正向兴趣，浏览代表弱兴趣，点踩、跳过和屏蔽代表负向信号。系统还结合行为发生时间进行衰减，使近期行为对画像影响更大。搜索行为记录用户主动检索意图，可与标签偏好共同用于查询类兴趣发现；浏览行为附带的停留时长可用于推断浅阅读或深度阅读倾向。

画像计算并不是简单统计用户点过哪些内容，而是把行为强度、内容标签、作者信息、互动类型和时间窗口放在一起聚合。UserBehaviorProfileService 会根据用户行为记录生成 BehaviorProfile，其中包含 topicPreferences、authorPreferences、engagementStyle、depthPreference、freshnessPreference、userStage 和 profileSummary 等字段。画像结果进一步输出 DynamicWeights，用于调节推荐公式中的互动分、标签匹配、文本相似度、协同过滤、热门话题和探索因子等权重。

用户阶段划分也是画像技术的一部分，其划分结果会影响动态权重的取值。冷启动用户的探索权重更高，活跃用户的个性化匹配和协同过滤权重更高。该逻辑与表 3-11 中的用户阶段划分保持一致。

### 3.7.3 TF-IDF 文本相似度与协同过滤实现

文本相似度由 TfIdfService 实现。系统先从内容文本中提取词项，统计每个词项在文档中的词频，再结合语料库中文档总数和包含该词项的文档数计算 IDF。用户兴趣向量主要根据用户已点赞或高价值互动内容的文本向量聚合得到，候选内容向量则根据候选帖子正文计算得到。随后系统使用余弦相似度比较用户兴趣向量与候选内容向量，并将结果作为 tfidfSimilarityBoost 加入推荐评分。

协同过滤由 CollaborativeFilteringService 实现。系统将用户与内容之间的行为记录转化为用户—内容交互矩阵，不同行为对应不同权重，例如转发、评论、点赞和浏览的权重依次降低，并结合时间衰减削弱较早行为的影响。系统根据加权余弦相似度计算用户之间的相似程度，再从相似用户喜欢或互动过的内容中生成协同推荐候选。当某条候选内容出现在协同推荐集合中时，混合推荐策略会给予该内容一定加成。

### 3.7.4 混合推荐排序与评分拆分实现

混合推荐策略由 HybridRecommendationStrategy 实现。该策略接收候选内容列表和当前用户 ID 后，会读取用户画像、负反馈、协同过滤结果和热门标签数据，对每条候选内容计算 ScoreBreakdown。ScoreBreakdown 不仅保存最终得分，也保存互动分、标签匹配、文本相似度、协同过滤、时间衰减、热门话题、作者偏好和随机扰动等分项，使推荐结果具有可解释性。

在排序完成后，系统还会进行作者多样性控制和加权随机探索。作者多样性主要避免同一作者内容连续出现；加权随机探索则避免信息流每次都完全固定，有助于发现用户潜在兴趣。通过“候选召回—负反馈过滤—分项打分—重排探索—结果返回”的处理流程，系统将用户行为、内容质量、兴趣匹配和多样性控制统一到推荐结果中。

### 3.7.5 WebSocket 实时通信实现

系统实时通信主要用于通知和私信。后端通过 WebSocketConfig 启用 WebSocket 与 STOMP 消息通道，并配置消息代理和用户目的地前缀。NotificationService 和 MessageService 在生成通知或私信记录后，使用 SimpMessagingTemplate 将消息推送到指定用户队列。前端建立连接后订阅对应队列，即可在用户在线时及时收到通知或私信。

该设计将消息持久化与实时推送结合起来。数据库记录保证通知和私信不会因用户离线而丢失，WebSocket 推送则提高在线场景下的消息到达及时性。如果连接失败，用户仍然可以通过 REST 接口查询通知列表、私信列表和未读数。后续若部署到公网环境，还需要在 WebSocket 握手阶段加强令牌校验和订阅权限控制，避免用户订阅不属于自己的消息队列。

### 3.7.6 AI 服务接入、缓存与降级实现

AI 功能通过后端统一接入 Ollama 服务。后端在配置文件中设置模型地址和模型名称，业务代码通过 HTTP 请求调用模型接口。AI 推荐策略会将用户画像摘要和候选内容摘要组织为 Prompt，并要求模型返回固定 JSON 结构。后端接收到响应后，需要提取 JSON、校验 ranking 字段、过滤无效内容 ID，并把推荐理由封装回响应对象。

为避免模型推理阻塞信息流主流程，系统在 AI 推荐模式中加入缓存和异步预计算思路。缓存命中时，系统直接返回已有 AI 推荐结果；缓存未命中时，系统优先返回传统混合推荐结果，并在后台触发 AI 推荐计算。若 Ollama 服务不可用、响应超时或返回格式无法解析，系统回退到传统推荐或基础互动排序。这样处理后，AI 模块成为推荐系统的增强能力，而不会成为基础信息流加载的单点风险。

### 3.7.7 数据统计与可视化实现

数据统计与可视化主要由后端统计接口和前端 ECharts 图表共同完成。后端 AnalyticsService 聚合用户数、内容数、行为记录、广告展示点击、行为类型分布、内容分类分布、内容标签分布、热门话题和用户兴趣标签等数据；前端 AnalyticsView、CompareView 和用户画像组件根据接口返回结果渲染折线图、柱状图、环形图、词云、雷达图和指标卡片。

算法可视化的重点不是单纯展示图表，而是把推荐过程中的中间指标暴露出来。例如推荐对比页面展示推荐流与时间倒序流的平均分、标签命中率、TF-IDF 均值、作者去重率和标签覆盖率；画像页面展示兴趣标签、互动风格和近期兴趣变化；统计中心展示行为类型分布和内容标签分布。这些可视化结果可以为第五章测试分析提供依据，使测试结论不只依赖主观观察，而是能够结合统计结果进行说明。
