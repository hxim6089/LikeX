## 一、项目基本信息

- **课题名称：** 基于用户行为分析的实时信息流排序与分发系统的设计与开发
- **核心目标：** 采集用户浏览、点赞、评论、转发、搜索和负反馈等行为，构建用户画像，并综合多种推荐信号生成个性化信息流。
- **技术架构：** Vue 3 + Spring Boot + Spring Data JPA + MySQL，使用 WebSocket 实现实时通知与私信，使用 ECharts 展示推荐效果和统计数据。
- **核心代码位置：**
  - 候选池构建：`RecommendationService`
  - 传统混合推荐：`HybridRecommendationStrategy`
  - 用户行为画像与动态权重：`UserBehaviorProfileService`
  - TF-IDF：`TfIdfService`
  - 协同过滤：`CollaborativeFilteringService`
  - 热门话题：`TrendingService`
  - AI 推荐：`AiRecommendationStrategy`、`AiRecCacheService`
  - 推荐策略切换：`RecommendationStrategyManager`
  - 统计分析：`AnalyticsService`、`CompareController`

## 二、答辩回答原则

回答老师问题时建议采用以下结构：

> **先说结论，再说实现机制，最后说验证方式或不足。**

示例：

> 本系统实现的是多策略融合的混合推荐，而不是单一协同过滤。系统先从关注作者和全站其他作者构建双源候选池，再经过负反馈过滤，最后综合互动热度、用户画像、TF-IDF、协同过滤、热门话题和时间衰减进行排序。推荐对比页通过推荐流与时间倒序流的指标差异验证个性化效果。

答辩时不要把系统描述成已经达到商业平台生产标准。可以说明系统完成了任务书要求的原型设计和核心链路，同时诚实指出数据规模、安全控制和大规模性能方面仍有扩展空间。

## 答辩现场项目展示流程与话术

### 总体思路

答辩演示不要按照侧边栏从上到下逐页介绍，而应围绕一条主线展开：

> **用户产生行为 → 系统构建画像 → 推荐算法生成排序 → 页面解释推荐原因 → 对比页面验证效果。**

建议总展示时间控制在 **7-9 分钟**。注册登录、普通发帖、通知、私信、广告和 AI 问答只需证明系统功能完整，不应占用大量时间。算法验证与用户画像应占演示时间的一半以上。

### 展示顺序总览

| 顺序 | 时间 | 展示页面或操作 | 主要目的 |
| --- | ---: | --- | --- |
| 1 | 30 秒 | 首页推荐流 | 说明系统定位和推荐结果 |
| 2 | 60 秒 | 首页推荐理由、点赞或负反馈 | 展示行为采集与推荐闭环 |
| 3 | 60 秒 | 个人主页 `Insights` | 展示综合用户画像 |
| 4 | 90 秒 | 算法验证页的当前用户行为画像 | 重点解释排序型画像和动态权重 |
| 5 | 90 秒 | 千人千面对比 | 证明不同用户获得不同权重和排序 |
| 6 | 120 秒 | 推荐流与时间倒序、管道漏斗、调参 | 重点解释混合推荐算法和验证方式 |
| 7 | 40 秒 | 管理页推荐策略切换 | 说明策略模式、AI 辅助与降级 |
| 8 | 30 秒 | 返回算法验证页或首页总结 | 收束系统核心贡献 |

### 第一步：首页说明系统定位

**展示动作：** 登录提前准备好的活跃用户，进入首页推荐流，停留在带有推荐理由和推荐评分的帖子。

**建议话术：**

> 各位老师好，我的课题是基于用户行为分析的实时信息流排序与分发系统。系统表面上是一个类 X 社交平台，但重点不是基础发帖页面，而是后面的推荐闭环。用户浏览、点赞、评论、转发和负反馈会形成行为数据，系统根据这些行为构建画像，再对候选内容进行个性化排序。当前首页展示的就是该用户的推荐结果。

**此时应指向：**

- 帖子排名和推荐评分；
- “你常看某话题”“你常互动的作者”等推荐理由；
- 推荐流与关注流的区别。

**不要展开：** 登录流程、页面样式和普通 CRUD 实现。

### 第二步：展示行为如何进入推荐闭环

**展示动作：** 对一条帖子进行点赞，或使用“减少此类内容推荐”等负反馈入口；再指出浏览行为会在帖子进入可视区域并停留后自动采集。

**建议话术：**

> 用户的操作不仅改变页面上的点赞数，还会写入统一的行为或负反馈数据。不同操作表达兴趣的强度不同，例如浏览属于弱信号，评论、转发属于更强信号；行为发生时间越早，进入画像时的影响也越低。下一次请求推荐结果时，这些数据会继续参与画像和排序计算。

**老师可能立即追问：**

- 浏览行为如何采集：使用 `IntersectionObserver` 判断帖子进入视野，并结合停留时间记录；
- 为什么行为权重不同：行为成本和表达兴趣强度不同；
- 为什么负反馈单独处理：强负反馈需要过滤内容或作者，而不只是降低普通兴趣分。

### 第三步：展示综合用户画像

**展示动作：** 打开个人主页，进入 `Insights`，展示兴趣词云、行为雷达图、分类偏好、活跃度和阅读偏好。

**建议话术：**

> 这里展示的是面向用户和管理员观察的综合画像，它将行为数据整理为兴趣词云、活跃度、阅读偏好和话题分布，便于直观看到系统如何理解用户。画像不是用户手工选择的标签，而是根据数据库中的内容、互动和浏览数据计算得到。

**重要区分：**

> 个人主页中的综合画像主要用于可视化展示；接下来算法验证页中的行为画像会直接生成动态权重并参与推荐排序。两者数据来源相关，但服务目的不同。

### 第四步：重点展示排序型行为画像与动态权重

**展示动作：** 打开“算法验证”页面，先停留在“当前用户行为画像”区域，依次指出用户阶段、互动风格、内容深度、新鲜度偏好、探索度、话题偏好和自动生成的推荐权重。

**建议话术：**

> 这一部分是系统推荐算法的入口。系统首先读取用户历史行为，并将用户划分为冷启动、初级和活跃三个阶段：行为少于 10 条时属于冷启动，少于 50 条时属于初级用户，达到 50 条后属于活跃用户。不同阶段使用不同策略，冷启动用户更依赖热门内容并提高探索比例；活跃用户则更依赖话题亲和度、作者亲和度、文本相似度和协同过滤。

> 在阶段判断之外，系统还会计算用户的话题偏好、作者偏好、互动风格、内容深度、新鲜度偏好和探索度。话题与作者偏好由“行为权重乘以时间衰减”累计得到；探索度根据话题偏好的归一化香农熵计算。画像最终会转换成该用户独立的动态权重，因此用户画像不是只用于展示，而是直接影响后续排序。

**一句话回答“画像如何影响推荐”：**

> 画像先生成动态权重，动态权重再决定话题、作者、文本相似度、热门度和协同过滤等信号在最终得分中的占比。

### 第五步：用千人千面证明画像真正参与排序

**展示动作：** 在“千人千面对比”中选择一个行为差异明显的用户，对比两人的画像属性、动态权重雷达图和 Top 5 推荐内容。

**建议话术：**

> 这里使用相同系统和内容库，对比两个行为历史不同的用户。可以看到两人的兴趣话题、互动风格和动态权重不同，最终 Top 5 推荐内容与推荐理由也不同。这说明系统不是给所有用户返回同一份热门列表，而是让画像实际进入了排序过程。

**选择对比用户的原则：**

- 当前用户应为行为较多的活跃用户；
- 对比用户应具有明显不同的话题偏好或处于冷启动、初级阶段；
- 答辩前确认两人的 Top 5 推荐结果确实存在明显差异。

### 第六步：重点讲解混合推荐算法与效果验证

**展示动作：** 向下滚动到推荐管道、推荐指标、个性化推荐与时间倒序对比区域。

**推荐算法主话术：**

> 系统采用的是混合推荐，不是只使用某一种算法。首先从用户已关注作者和全站其他作者构建双候选源，并进行去重、回复过滤和负反馈过滤。然后对每条候选内容综合计算互动热度、关注关系加成、话题与作者亲和度、标签匹配、TF-IDF 文本相似度、热门话题、内容深度、新鲜度和协同过滤加成，再应用时间衰减和已浏览、已点赞、已点踩、已跳过等交互惩罚。排序后还会进行作者多样性处理和可控探索，最终形成分发结果。

**推荐算法四步概括：**

1. **候选召回：** 关注作者内容与全站其他内容组成双源候选池；
2. **过滤处理：** 去重、过滤回复、隐藏内容和屏蔽作者；
3. **混合排序：** 多行为、画像、TF-IDF、协同过滤、热门度和时间因素共同打分；
4. **最终分发：** 加入作者多样性和探索机制，截取结果返回用户。

**验证页面话术：**

> 为了验证排序是否产生差异，系统使用同一用户和同一内容范围，对比个性化排序与时间倒序。页面展示前 20 条内容的推荐平均分、标签命中率、TF-IDF 相似度、平均互动量、作者去重率和标签覆盖率。个性化提升倍率是内部评分对比，不等同于真实线上 CTR，但可以用于说明排序结果比单纯时间倒序更符合当前用户画像。

**漏斗图话术：**

> 管道漏斗用于解释推荐内容从全量候选到最终分发的过程。滑块调节的是排序权重，因此会影响评分结果、排序截断和下方对比指标；候选来源和负反馈过滤由数据库内容、关注关系和负反馈记录决定，通常不会因评分权重变化。

**调参演示建议：**

- 只选择一个预设方案，或明显提高“个性化加成”；
- 指出 Top 推荐顺序、推荐平均分和排序截断数字的变化；
- 不要连续随意拖动多个滑块，以免老师无法理解变化原因；
- 说明调参只用于算法验证页的临时实验，不会直接覆盖全局推荐策略。

### 第七步：展示策略切换与 AI 降级

**展示动作：** 打开管理页面，展示传统推荐与 AI 推荐策略切换区域，不必长时间等待 AI 推理。

**建议话术：**

> 推荐模块使用策略模式组织，传统混合推荐负责稳定主链路，AI 推荐作为可切换的辅助策略。AI 推理耗时较高，因此系统采用异步计算与缓存；首次缓存未命中时可以先返回传统结果，AI 服务不可用时也不会阻塞基础推荐功能。

### 第八步：结束总结

**建议话术：**

> 综上，本系统完成的不只是社交平台基础功能，而是一条可以运行和解释的推荐闭环：用户行为形成画像，画像生成动态权重，双源候选经过混合排序和过滤后完成分发，算法验证页面再对排序结果进行对比和解释。系统重点体现了用户画像、混合推荐和工程化验证三个方面。

### 时间不足时的 5 分钟精简路线

## 三、高频必问问题

### 1. 你的毕业设计主要解决了什么问题？

**参考回答：**

本设计主要解决传统时间倒序信息流无法体现用户兴趣差异的问题。系统采集用户的浏览、点赞、评论、转发、搜索和负反馈等行为，将这些行为转化为用户兴趣画像，再综合内容热度、关注关系、文本相似度、协同过滤、热门话题和时间因素，对信息流进行个性化排序与分发。

### 2. 你的系统与普通社交平台有什么区别？

**参考回答：**

普通社交平台主要完成注册、发帖、评论和关注等业务功能，而本系统的重点是让这些业务行为进入推荐闭环。用户每次浏览或互动都会形成行为数据，行为数据用于更新画像和调整推荐权重，推荐结果又会影响后续行为。同时系统提供评分明细、推荐流与时间流对比、管道漏斗和统计分析，用于解释和验证推荐过程。

### 3. 为什么选择这个课题？

**参考回答：**

社交媒体内容量持续增加，单纯时间倒序容易造成信息过载。推荐系统能够将软件工程、数据建模、算法设计、前后端开发和可视化分析结合起来。本课题既具有实际应用价值，也能够完整体现从需求分析、系统设计、编码实现到测试验证的软件工程开发过程。

### 4. 为什么称为“实时信息流”？

**参考回答：**

这里的“实时”不是指实时训练大型机器学习模型，而是指用户请求信息流时，系统会读取当前行为、画像、关注关系、内容热度和负反馈状态，实时计算或获取最新排序结果。用户的新行为还会影响后续请求中的画像和权重；通知与私信则通过 WebSocket 实时推送。

### 5. 系统整体架构是什么？

**参考回答：**

系统采用 B/S 前后端分离架构。Vue 3 前端负责页面交互和图表展示，通过 Axios 调用 Spring Boot REST API；Spring Boot 后端按照 Controller、Service、Repository 分层组织业务；MySQL 保存用户、内容、行为、标签、通知、广告等数据；WebSocket 负责实时消息；Ollama 和 DeepSeek 用于 AI 辅助功能。

### 6. 为什么使用 Spring Boot 和 Vue 3？

**参考回答：**

Spring Boot 便于快速构建 REST 接口，并能够结合 Spring Data JPA、Spring Security 和 WebSocket 组织后端业务。Vue 3 组件化程度较高，适合构建单页应用；Element Plus 和 ECharts 可以提高管理页面和可视化页面的开发效率。前后端分离也便于独立调试、接口测试和后续扩展。

### 7. 你认为系统最核心的模块是什么？

**参考回答：**

最核心的是“行为采集—画像构建—候选生成—混合排序—结果展示”的推荐链路。基础社交功能为推荐系统提供数据来源，推荐服务负责把这些行为数据转化为排序结果，算法验证和统计分析模块负责解释与验证结果。

## 四、推荐算法重点问题

### 8. 什么是混合推荐？你的系统“混合”体现在哪里？

**参考回答：**

混合推荐是将多种推荐方法和业务信号融合到同一条推荐链路中。本系统的融合体现在三个层次：候选层融合关注作者与全站其他作者两类来源；排序层融合多行为互动、用户画像、TF-IDF、协同过滤、热门话题和时间因素；分发层再加入负反馈、作者多样性和探索机制。因此它不是分别展示几个算法结果，而是让多种信号共同决定同一份最终信息流。

### 9. 双候选源是什么意思？

**参考回答：**

双候选源分为网内候选和网外候选。网内候选是用户已关注作者发布的内容，网外候选是全站其他内容。`RecommendationService` 分别获取两类候选，对内容去重并过滤回复、隐藏内容和被屏蔽作者，然后合并为候选池。网内内容在评分时会获得额外加成，但网外内容仍然可以通过兴趣匹配和内容质量进入推荐结果。

### 10. 为什么不能只推荐关注用户的内容？

**参考回答：**

只推荐关注用户的内容虽然稳定，但容易造成候选不足和信息封闭。引入网外候选可以帮助用户发现新作者和新话题。系统通过网内加成保证关注关系的重要性，同时通过网外候选和探索机制提升内容覆盖率和新颖性。

### 11. 最终推荐分是如何计算的？

**参考回答：**

系统先根据点赞、评论、转发和浏览计算基础互动分，再使用互动率修正内容质量，并对关注作者内容进行网内加成。在此基础上增加话题亲和度、作者亲和度、标签匹配、TF-IDF 相似度、热门话题、内容深度匹配、新鲜度匹配和协同过滤加成，最后应用时间衰减、互动惩罚、作者多样性惩罚和探索随机性。其中各项权重不是所有用户共用一套固定值，而是由用户行为画像生成，并可在算法验证页使用临时参数进行对比实验。

可以用下面的抽象公式说明：

```text
最终得分 =
（基础互动分 × 互动率修正 × 网内加成）÷ 时间衰减
+ 标签与话题亲和度
+ 作者亲和度
+ TF-IDF 相似度
+ 热门话题加成
+ 协同过滤加成
+ 新鲜度与深度匹配
+ 探索随机项
```

### 12. 为什么不同行为要设置不同权重？

**参考回答：**

不同行为表达兴趣的强度不同。浏览通常是弱信号，点赞表示明确正向反馈，评论和转发需要更高的参与成本，因此权重更高。差异化权重可以避免大量低价值浏览行为淹没更有意义的互动行为。

### 13. 为什么浏览量图标点击没有作用？

**参考回答：**

该图标不是操作按钮，而是帖子的浏览量统计展示。浏览行为通过帖子进入用户可视区域并停留一定时间自动记录，而不是通过点击浏览量图标记录。这样更符合信息流场景，因为用户阅读帖子时不一定会点击帖子。界面上应通过提示和鼠标样式明确它是统计项。

### 14. 浏览行为如何采集？

**参考回答：**

前端使用 `IntersectionObserver` 判断帖子是否进入可视区域。当帖子可见比例达到设定条件并停留约两秒后，前端调用浏览行为接口，记录用户 ID、内容 ID 和停留时长。较短时间快速滑过的内容可以记录为跳过行为，用于后续降权。

### 15. 用户画像是如何构建的？

**参考回答：**

系统中可以将画像分为两个用途。个人主页的综合画像用于可视化展示兴趣词云、活跃度和阅读偏好；算法验证页的行为画像直接服务于推荐排序。排序型画像首先读取 Behavior 表中的历史行为并关联具体内容，再提取标签、分类、作者、发布时间和内容长度等特征。话题与作者偏好按“行为权重 × 时间衰减”累计；互动风格根据点赞、评论、转发和浏览占比判断；内容深度根据互动内容长度与停留时长判断；新鲜度根据用户互动内容的发布时间计算；探索度根据话题分布的归一化香农熵计算。最终画像会进一步生成动态推荐权重。

### 16. 页面中显示的“初级用户”是什么意思？

**参考回答：**

初级用户不是权限角色，也不是用户年龄，而是推荐系统根据行为数量划分的用户阶段。当前实现中，行为少于 10 条属于冷启动用户，10 到 49 条属于初级用户，达到 50 条及以上属于活跃用户。不同阶段使用不同动态权重：冷启动更依赖热门和探索，活跃用户更强调个性化和协同过滤。

### 17. 为什么要使用动态权重？

**参考回答：**

固定权重无法适应不同用户的数据丰富程度和行为习惯。系统先根据行为数量判断用户阶段，再结合互动风格、内容深度、新鲜度偏好和探索度调整权重。冷启动用户缺少画像，因此提高热门内容和探索比例；初级用户逐步增加话题与作者偏好；活跃用户则提高话题亲和度、文本相似度和协同过滤权重。动态权重是用户画像真正进入推荐排序的连接点。

### 18. TF-IDF 在系统中起什么作用？

**参考回答：**

标签匹配只能识别已标注的主题，TF-IDF 可以进一步比较正文文本。系统将用户点赞内容的 TF-IDF 向量进行加权平均，形成用户文本兴趣向量，再计算候选帖子向量与用户向量的余弦相似度，并将相似度作为排序加成。它用于发现标签不同但文本语义接近的内容。

### 19. 为什么选择 TF-IDF，而不是直接使用深度学习文本模型？

**参考回答：**

TF-IDF 实现简单、计算过程清晰、可解释性强，适合当前毕业设计的数据规模和答辩展示。深度文本模型通常需要更多训练数据、算力和评估工作。本系统同时保留了 AI 辅助重排作为扩展，但主推荐链路使用轻量且稳定的算法保证可运行性。

### 20. 协同过滤是如何实现的？

**参考回答：**

系统采用基于用户的协同过滤。首先将用户对内容的浏览、点赞、评论、转发等行为转换为带权行为向量，并使用指数时间衰减降低旧行为影响；然后计算目标用户与其他用户之间的加权余弦相似度；最后选择相似用户互动过、但目标用户未互动的内容作为协同过滤候选或加分项。

### 21. 协同过滤与 TF-IDF 有什么区别？

**参考回答：**

TF-IDF 基于内容文本相似性，回答“这篇内容是否接近用户过去喜欢的文本”；协同过滤基于用户行为相似性，回答“与该用户行为相似的人喜欢什么”。前者能够处理内容语义，后者能够发现用户没有直接表达过的潜在兴趣，两者融合可以互相补充。

### 22. 热门话题是如何产生的？是每个用户独立的吗？

**参考回答：**

当前热门话题是全站统计，不是每个用户独立生成。`TrendingService` 默认统计最近 24 小时内容中的标签，根据相关帖子数量和互动量计算热度分，再返回 Top10。用户个人兴趣 Top 标签属于用户画像，两者概念不同。推荐排序会将全站热门话题作为一项加成，但不会直接替代个性化兴趣。

### 23. 时间衰减为什么采用分段函数？

**参考回答：**

信息流内容具有明显生命周期。新内容需要较高曝光，但高质量旧内容也不能立即消失。因此系统将内容生命周期划分为 0 至 6 小时、6 至 24 小时、24 至 72 小时和 72 小时以上几个阶段，逐步提高衰减程度，并在长尾阶段使用对数衰减，兼顾时效性和历史优质内容价值。

### 24. 为什么还要加入随机性？随机性会不会破坏推荐效果？

**参考回答：**

如果完全按照固定分数排序，用户每次刷新看到的内容可能相同，并且容易形成信息茧房。系统采用基于分数的加权随机采样，高分内容被选中的概率更大，低分但可能有价值的内容也有少量曝光机会。随机性受到探索因子控制，冷启动用户探索更多，活跃用户推荐更稳定。

### 25. 如何保证推荐内容的多样性？

**参考回答：**

系统对同一作者重复出现的内容进行递减惩罚，同一作者第 2 次出现后分数会按比例下降；同时引入网外候选和加权随机采样，避免内容完全被高热度作者占据。算法验证页还计算作者去重率和标签覆盖率，用于观察推荐结果是否过于集中。

### 26. 负反馈如何参与推荐？

**参考回答：**

负反馈分为候选过滤和排序降权两类。不感兴趣、屏蔽和静音等强负反馈会在候选池构建阶段过滤相应内容或作者；点踩、已浏览、已点赞和快速滑过等行为会在评分阶段降低内容优先级，从而减少重复或不符合兴趣的内容。

### 27. 为什么已点赞内容还要降权？

**参考回答：**

点赞说明用户认可该内容，但用户通常不需要反复看到同一帖子。系统保留该内容的正向兴趣信号，用于画像和协同过滤，同时降低它在后续信息流中的优先级，以平衡兴趣学习与重复推荐控制。

## 五、算法验证与统计分析问题

### 28. 如何证明个性化推荐比时间倒序更有效？

**参考回答：**

系统在算法验证页对同一用户、同一候选范围下的个性化推荐流和时间倒序流进行对比。时间流仍计算各内容的推荐分，但最终保持按发布时间排序，因此可以作为基线。页面比较前 20 条内容的平均推荐分、标签命中率、TF-IDF 相似度、平均互动量、作者去重率和标签覆盖率，并同时展示两个用户的画像、动态权重和 Top 5 推荐差异。这能够证明画像与混合排序机制确实改变了结果，但由于当前主要使用模拟数据，不能将其表述为真实线上 CTR 提升。

### 29. 个性化提升倍率是什么？

**参考回答：**

个性化提升倍率用于表示个性化推荐平均得分相对于时间倒序结果平均得分的提升程度。它是一个对比指标，不代表真实线上点击率提升。答辩时应说明该指标用于当前模拟数据和系统内部评分对比，不能直接等同于商业平台的用户留存提升。

### 30. 管道漏斗图展示了什么？

**参考回答：**

漏斗图展示推荐请求从全量候选到最终分发的处理过程，包括全量帖子、关注作者与全站其他作者组成的双源候选、负反馈过滤、排序质量线截断和最终分发。它的作用是把推荐算法从一个最终分数展开为可解释的处理管道，说明系统不是直接对全部内容排序后原样返回。

### 31. 为什么调节滑块后漏斗数字会变化？

**参考回答：**

权重变化会改变候选内容的评分分布，从而改变超过动态质量线的候选数量，因此“排序质量线截断”阶段和下方对比指标可能变化。全量候选、来源拆分和负反馈过滤分别由数据库内容、关注关系和负反馈记录决定，不应随着评分权重变化；最终分发数量则受页面返回上限控制。滑块只用于算法验证页的临时实验，不会直接修改全局推荐策略。

### 32. 统计数据是真实数据还是写死的？

**参考回答：**

统计数据主要由后端从用户、内容、行为、标签、负反馈和广告等数据表中聚合计算，再由前端 ECharts 展示。部分测试数据由系统种子数据或外部数据导入生成，但图表指标不是前端静态写死的数据。

### 33. 为什么使用模拟数据？模拟数据是否能证明算法有效？

**参考回答：**

毕业设计无法获得大规模真实平台用户数据，因此使用多类型模拟用户、内容和行为数据验证功能链路与排序差异。模拟数据能够证明系统机制可运行、不同画像能够产生不同排序结果，但不能替代真实线上 A/B 测试。后续可通过真实数据和 NDCG、Recall、CTR 等指标进行更严格评估。

## 六、AI、广告与实时通信问题

### 34. AI 推荐与传统推荐是什么关系？

**参考回答：**

系统采用策略模式管理传统推荐和 AI 推荐。传统推荐负责稳定的候选生成和多因子排序；AI 推荐根据用户画像和候选内容进行语义重排。AI 不是唯一推荐链路，首次请求或 AI 不可用时会返回传统推荐结果，后台异步计算 AI 结果并缓存。

### 35. 为什么不直接全部使用大模型推荐？

**参考回答：**

大模型推理延迟和资源消耗较高，输出还可能不稳定。如果首页完全依赖大模型，一旦模型不可用，主流程就会受到影响。因此系统使用传统算法保证效率、可解释性和可用性，将大模型定位为语义理解和辅助重排模块。

### 36. AI 服务不可用时系统怎么办？

**参考回答：**

AI 推荐缓存未命中时，系统先返回传统混合推荐结果，并异步触发 AI 计算；如果 Ollama 调用失败或返回格式无法解析，也会回退到传统排序。这样可以避免 AI 服务故障阻塞首页信息流。

### 37. 广告如何进行智能分发？

**参考回答：**

广告服务先获取用户画像中的兴趣标签，再计算广告标签匹配数量、广告出价和历史 CTR 质量分。广告综合分由标签匹配、出价和质量分共同构成，按得分排序后返回；前端再按照后台配置的间隔插入信息流，并记录曝光和点击。

### 38. WebSocket 在系统中用在哪里？

**参考回答：**

WebSocket 用于实时通知和私信。后端在发生点赞、评论、关注或私信时，通过 `SimpMessagingTemplate.convertAndSendToUser` 推送到用户专属队列；前端使用 STOMP over SockJS 订阅对应队列并更新未读数量或显示通知。

## 七、数据库与软件工程问题

### 39. 为什么单独设计 Behavior 行为表？

**参考回答：**

帖子表中的点赞数和浏览数只能表示聚合结果，无法说明是哪个用户、在什么时间、对什么内容执行了何种行为。Behavior 表保存用户 ID、内容 ID、行为类型、停留时长和时间戳，能够支撑用户画像、协同过滤、时间衰减、负反馈判断和统计分析。

### 40. 内容表为什么有 parent、repostOf 和 quoteOf？

**参考回答：**

这三个自关联字段表达不同内容关系。`parent` 用于评论和多级回复，`repostOf` 表示无附加内容的转发来源，`quoteOf` 表示带用户观点的引用来源。使用自关联可以复用内容实体，同时保留互动链路。

### 41. 系统如何进行模块解耦？

**参考回答：**

后端通过 Controller、Service 和 Repository 分层；推荐算法通过 `RecommendationStrategy` 统一接口和 `RecommendationStrategyManager` 管理不同策略；画像、TF-IDF、协同过滤、热门话题和广告分别由独立服务负责。前端将信息流、评分面板、漏斗图、画像图表等拆分为组件，便于维护和复用。

### 42. 为什么使用策略模式？

**参考回答：**

传统混合算法和 AI 算法的输入输出形式相近，但内部实现不同。策略模式允许控制层通过统一接口调用当前策略，管理员切换算法时无需修改推荐接口，也便于以后增加新的实验策略。

### 43. 系统如何处理异常？

**参考回答：**

前端 Axios 封装负责统一提示接口错误；后端服务对数据不存在、AI 调用失败和导入异常等情况进行处理。AI 推荐具有回退机制，外部数据导入失败时也可以使用系统种子数据或内置数据。正式生产环境还应补充更完整的异常码、日志监控和重试机制。

### 44. 系统是否实现了权限控制？

**参考回答：**

系统实现了普通用户和管理员角色区分，前端路由和侧边栏会限制管理员页面入口，部分业务操作也会在服务层校验角色，例如管理员可以删除其他用户内容。需要诚实说明，当前 Spring Security 使用 JWT 软校验并允许请求进入，属于毕业设计演示阶段的简化实现；生产环境应在后端接口层增加严格的角色授权和未认证请求拦截。

### 45. 用户密码是否安全存储？

**参考回答：**

当前原型系统的密码校验采用了开发阶段简化方式，尚未使用 BCrypt 哈希存储。正式部署时必须使用 BCrypt 等单向哈希算法，并增加密码复杂度、登录限流、Token 过期与刷新等安全机制。这是当前系统明确需要加强的部分。

## 八、老师可能追问的尖锐问题

### 46. 你的算法是自己设计的吗？

**参考回答：**

系统整体混合排序流程和工程实现由我结合课题要求设计完成，但其中使用的 TF-IDF、余弦相似度、协同过滤、时间衰减和加权随机采样都是已有推荐方法。我的工作主要是结合类 X 信息流场景，将这些方法组织成可运行、可解释、可调参和可验证的推荐链路，而不是声称提出了全新的理论算法。

### 47. 你的系统能支持大规模用户吗？

**参考回答：**

当前系统定位为毕业设计原型，能够满足现有模拟数据和功能演示，但部分计算会读取较多内容和行为数据，尚未针对百万级数据优化。面向大规模场景需要增加离线画像计算、特征缓存、候选索引、消息队列、分布式缓存和召回服务，并避免请求时全量扫描。

### 48. 推荐算法的复杂度如何？

**参考回答：**

当前候选池规模为 \(N\) 时，多因子评分主要需要遍历候选内容，基础排序约为 \(O(N \log N)\)。TF-IDF 和协同过滤还会受到语料规模、行为数量和用户数量影响。当前实现适合原型数据规模；大规模场景应将画像、IDF、相似用户和热门话题离线计算或缓存。

### 49. 为什么没有使用准确率、召回率或 NDCG？

**参考回答：**

准确率、召回率和 NDCG 需要可靠的真实反馈或训练测试集作为相关性标注。当前系统主要使用模拟数据，因此采用标签命中率、TF-IDF 相似度、平均推荐分、互动量和多样性指标进行机制验证。后续获得真实行为数据后，可以按时间切分训练集和测试集，引入 Recall@K、NDCG@K 和 CTR 等指标。

### 50. 推荐结果为什么每次刷新不同？如何复现实验？

**参考回答：**

系统为平衡探索和利用加入了随机抖动及加权随机采样，因此普通推荐流刷新时可能不同。算法验证页通过同一用户、同一组参数和同一候选池进行对比，能够观察整体指标变化。若需要严格复现实验，可以固定随机种子或在实验模式关闭随机探索。

### 51. 如果一个新用户没有任何行为，系统如何推荐？

**参考回答：**

新用户被划分为冷启动阶段，系统提高热门话题和探索权重，降低依赖用户个性化画像、文本相似度和协同过滤的程度。同时仍保留网内内容和高质量内容，随着用户产生行为，系统逐步切换为更个性化的动态权重。

### 52. 热门内容会不会一直占据推荐前列？

**参考回答：**

系统没有只按互动量排序。热门内容会受到时间衰减、作者多样性、用户兴趣匹配、负反馈和探索机制共同影响。对于活跃用户，热门权重还会降低，而个性化和协同过滤权重会提高，从而缓解流行度偏置。

### 53. 系统中哪些功能是真正“实时”的，哪些不是？

**参考回答：**

通知和私信通过 WebSocket 实时推送；用户请求推荐流时会使用当前数据进行即时排序；浏览和互动行为也会在发生后写入系统。画像和算法权重是按请求读取行为后计算，并非持续流式训练模型。答辩时应明确区分实时业务响应和在线模型训练。

### 54. 系统当前最大的不足是什么？

**参考回答：**

主要不足有三点：第一，数据规模和用户规模有限，算法效果主要通过模拟数据验证；第二，推荐链路仍包含请求时计算，面向大规模数据需要缓存和离线计算；第三，安全控制属于原型级实现，密码加密和后端严格鉴权仍需完善。后续可以增加真实数据评估、A/B 测试、深度推荐模型和生产级安全机制。

## 九、演示过程中可能出现的问题与回答

### 55. 为什么浏览量旁边的图标不能点击？

**参考回答：**

它是浏览量统计展示，不是功能按钮。浏览通过帖子进入视野并停留一定时间自动采集。为了避免误解，界面可以进一步增加“浏览量”悬浮提示，并取消可点击按钮式的悬浮效果。

### 56. 为什么调整部分滑块后，漏斗前几层数字不变化？

**参考回答：**

全量候选、网内网外来源和负反馈过滤由内容库、关注关系及负反馈数据决定，不直接受评分权重影响。滑块主要改变评分结果和排序截断，因此更可能影响漏斗后半部分以及推荐指标，而不是候选池来源数量。

### 57. 为什么 AI 推荐第一次请求没有明显变化？

**参考回答：**

AI 推理耗时较高，系统采用缓存与异步计算机制。缓存未命中时先返回传统推荐结果，后台计算 AI 排序并写入缓存，后续请求才能快速返回 AI 结果。这样可以保证首页不会因为模型推理被阻塞。

### 58. 为什么热门话题和某个用户兴趣 Top10 不一致？

**参考回答：**

热门话题是最近 24 小时的全站内容与互动统计；用户兴趣 Top10 是根据某个用户的历史行为和时间衰减计算的个人画像。两者的数据范围和用途不同，所以结果不必一致。

### 59. 为什么推荐分数看起来很大？

**参考回答：**

推荐分是多个因子加权后的内部排序分，不是概率，也不要求位于 0 到 1。它的主要作用是比较同一推荐请求中候选内容的相对优先级。若用于跨实验直接比较，需要进一步进行归一化。

### 60. 如果演示时后端端口被占用怎么办？

**参考回答：**

系统后端默认使用 8888 端口。如果启动提示端口被占用，应先定位并关闭占用进程，或统一修改后端端口、前端 API 地址、WebSocket 地址和 CORS 配置。不能只修改其中一个位置，否则会造成登录或实时通信失败。

## 十三、技术基础与八股追问

### Java 与 Spring Boot

### 61. Spring 和 Spring Boot 有什么区别？

**参考回答：**

Spring 提供 IoC、AOP、事务管理等基础能力，Spring Boot 在此基础上通过自动配置、Starter 依赖和内嵌服务器降低项目配置成本。本系统使用 Spring Boot 快速构建 REST 接口，并统一集成 JPA、Security 和 WebSocket 等组件。

### 62. 什么是 IoC 和依赖注入？

**参考回答：**

IoC 是将对象的创建和生命周期交给 Spring 容器管理；依赖注入是容器把对象所需的依赖传入对象。本系统的 Controller、Service 和 Repository 由容器管理，并主要通过构造器注入建立依赖关系，从而降低模块耦合。

### 63. 为什么推荐使用构造器注入？

**参考回答：**

构造器注入可以明确类的必要依赖，使依赖在对象创建时就完整可用，也更方便单元测试和替换实现。如果缺少必要依赖，程序会在启动阶段直接暴露问题，而不是运行到某个业务流程时才报错。

### 64. `@Controller` 和 `@RestController` 有什么区别？

**参考回答：**

`@Controller` 通常用于返回页面视图，方法若要直接返回 JSON 还需配合 `@ResponseBody`；`@RestController` 相当于两者组合，默认将返回值写入响应体。本系统采用前后端分离架构，因此接口控制器主要使用 `@RestController` 返回 JSON。

### 65. Controller、Service 和 Repository 分别负责什么？

**参考回答：**

Controller 负责接收请求、解析参数并返回结果；Service 负责业务规则和算法流程；Repository 负责数据库访问。以推荐请求为例，Controller 接收用户和分页参数，Service 完成候选召回、过滤与排序，Repository 查询内容、行为和关系数据。

### 66. 什么是 AOP？本项目可能在哪些地方使用？

**参考回答：**

AOP 是面向切面编程，用于将日志、事务、权限等横切逻辑从业务代码中分离。项目中的 `@Transactional` 就是典型应用，Spring 通过代理在方法执行前后管理事务提交和回滚。

### 67. `@Transactional` 有什么作用？

**参考回答：**

它用于保证一组数据库操作在同一事务中执行，成功时统一提交，出现异常时回滚。本系统在行为记录、负反馈和部分内容操作中使用事务，避免只更新一部分数据而造成状态不一致。

### REST 接口与系统安全

### 68. 什么是 RESTful API？

**参考回答：**

REST 是一种面向资源的接口设计风格，通常使用 URL 表示资源，并使用 HTTP 方法表达操作。系统前端通过 Axios 调用后端 REST 接口，使用 JSON 交换用户、内容、行为和推荐结果等数据。

### 69. GET、POST、PUT 和 DELETE 一般如何使用？

**参考回答：**

GET 用于查询资源，POST 用于创建资源或提交复杂操作，PUT 用于整体更新，DELETE 用于删除资源。GET、PUT 和 DELETE 通常应具有幂等性，即重复执行后的最终状态应保持一致；POST 一般不保证幂等。

### 70. 为什么接口层不应直接暴露全部实体对象？

**参考回答：**

直接暴露实体容易泄露密码、内部状态等字段，也会让数据库结构与前端接口强耦合。更规范的方式是使用 DTO 控制输入输出。本系统在推荐评分明细、管道统计和内容评分结果等接口中使用专门的数据结构组织返回值。

### 71. JWT 的基本原理是什么？

**参考回答：**

JWT 通常由 Header、Payload 和 Signature 三部分组成。用户登录后，后端签发包含用户标识和过期时间的 Token；前端后续请求在 `Authorization` 请求头中携带 Token，后端验证签名和有效期后识别用户身份。JWT 适合无状态接口，但不应在 Payload 中存放敏感明文。

### 72. 认证和授权有什么区别？

**参考回答：**

认证解决“当前用户是谁”，授权解决“该用户能做什么”。本系统当前通过 JWT 完成身份软校验，但 Spring Security 配置仍对请求整体放行，因此属于毕业设计原型；生产环境应进一步按照普通用户和管理员角色严格限制接口访问。

### 73. 为什么会出现 CORS 跨域错误？

**参考回答：**

浏览器的同源策略要求协议、主机和端口全部一致。前端运行在 `localhost:5173`，后端运行在 `localhost:8888`，两者端口不同，因此后端必须显式允许前端来源。`localhost`、`127.0.0.1` 以及不同端口都属于不同 Origin，配置不一致就会导致预检请求失败。

### 74. 为什么前端使用 Axios 拦截器？

**参考回答：**

拦截器可以统一处理所有请求和响应，减少页面中的重复代码。本系统通过请求拦截器自动添加 JWT，并根据普通 JSON 或文件上传设置请求头；响应拦截器负责统一提取错误信息并显示提示。

### JPA 与 MySQL

### 75. JPA 和 Hibernate 是什么关系？

**参考回答：**

JPA 是 Java 持久化规范，定义实体映射和数据访问的标准；Hibernate 是常用的 JPA 实现。Spring Data JPA 又在 JPA 基础上提供 Repository 抽象，使系统可以通过接口和方法命名完成常见数据库操作。

### 76. 懒加载和立即加载有什么区别？

**参考回答：**

立即加载会在查询主实体时同步加载关联数据，使用方便但可能查询过多；懒加载只在真正访问关联字段时查询，能够减少初始开销，但可能产生 N+1 查询或脱离事务后无法加载的问题。推荐列表数据量较大时，应根据实际使用字段设计查询，而不是无条件加载全部关联对象。

### 77. 什么是 N+1 查询问题？

**参考回答：**

先查询一次列表，再为列表中的每条数据分别查询关联对象，就会形成一次加 N 次查询。它会随数据量增长明显降低性能。可通过联表查询、批量查询、实体图或 DTO 投影减少数据库往返次数。

### 78. 数据库索引有什么作用？应给哪些字段建立索引？

**参考回答：**

索引通过额外的数据结构提高查询和排序效率，但会占用空间并增加写入成本。对于本系统，可重点考虑行为表的用户 ID、内容 ID、行为类型和时间字段，以及内容表的作者 ID、创建时间等高频筛选字段，并根据真实查询语句联合设计索引。

### 79. 为什么既要保存帖子计数，又要保存行为明细？

**参考回答：**

点赞数、评论数等聚合计数适合页面快速展示，但无法说明“谁在何时对什么内容进行了什么操作”。统一行为明细可以支持用户画像、时间衰减、协同过滤和数据复核，因此两类数据用途不同，不能完全相互替代。

### 80. 为什么列表接口需要分页？

**参考回答：**

如果一次查询并返回全部内容，会增加数据库、网络和浏览器渲染压力。分页只获取当前需要的数据。本系统使用 `PageRequest` 和分页参数处理内容、搜索、通知等列表，信息流再通过逐页加载形成连续浏览体验。

### 缓存、并发与实时通信

### 81. 为什么系统需要缓存？

**参考回答：**

热门话题、用户画像和 AI 推荐等结果计算成本较高，但短时间内不会剧烈变化，缓存可以减少重复计算并降低响应时间。本系统为热门话题和画像等数据设置缓存，AI 推荐缓存还配合过期时间和异步刷新使用。

### 82. 缓存可能带来什么问题？

**参考回答：**

缓存可能导致数据短暂不一致，还可能出现缓存穿透、击穿和雪崩。当前系统主要通过 TTL 和重新计算控制缓存有效期；若扩展到生产规模，还需要增加主动失效、热点保护、分布式缓存和监控机制。

### 83. `ConcurrentHashMap` 和普通 `HashMap` 有什么区别？

**参考回答：**

普通 `HashMap` 不保证多线程并发访问安全；`ConcurrentHashMap` 支持线程安全的并发读写，并尽量减少锁竞争。本系统在 AI 推荐缓存和广告频次控制中使用它，避免多个请求同时更新共享数据时破坏内部状态。

### 84. `AtomicBoolean` 在 AI 推荐缓存中有什么作用？

**参考回答：**

它通过原子操作标记某个用户的 AI 推荐是否正在计算。多个请求同时发生缓存未命中时，只有第一个请求能够启动计算，其余请求继续使用降级结果，从而避免重复调用模型造成资源浪费。

### 85. `@Async` 为什么适合 AI 推荐计算？

**参考回答：**

AI 推理耗时较长，如果同步执行会阻塞接口响应。系统使用 `@Async` 将 AI 排序放入后台线程：当前请求先返回传统混合推荐结果，计算完成后写入缓存，后续请求再使用 AI 结果，从而兼顾可用性和响应速度。

### 86. WebSocket 与普通 HTTP 有什么区别？

**参考回答：**

HTTP 通常由客户端发起请求、服务器返回响应；WebSocket 建立连接后允许客户端和服务器双向通信，适合实时通知和私信。本系统的普通业务接口使用 HTTP，消息和通知提醒通过 WebSocket 推送。

### 87. STOMP 和 SockJS 分别起什么作用？

**参考回答：**

STOMP 为 WebSocket 消息定义发送、订阅和目的地址等语义；SockJS 在浏览器或网络环境不完全支持 WebSocket 时提供兼容回退。本系统通过 `/topic`、`/queue` 和 `/user` 等目的地址区分广播消息与用户专属消息。

### Vue 前端与工程化

### 88. Vue 3 的响应式原理是什么？

**参考回答：**

Vue 3 主要使用 Proxy 代理响应式对象，在读取数据时收集依赖，在数据变化时触发相关视图更新。项目使用 Composition API 组织页面状态和生命周期逻辑，使推荐流、通知和管理页面的功能更容易拆分与复用。

### 89. `ref`、`computed` 和 `watch` 分别适合什么场景？

**参考回答：**

`ref` 用于保存响应式状态；`computed` 用于根据已有状态计算派生值，并具有缓存；`watch` 用于在状态变化后执行请求、持久化等副作用。选择原则是：数据本身用 `ref`，可推导结果用 `computed`，变化后要做额外操作时用 `watch`。

### 90. Vue 组件为什么要拆分？

**参考回答：**

组件化可以将界面和交互划分为职责清晰、可复用的单元，通过 Props 接收数据、通过事件向父组件传递操作。本系统将帖子卡片、信息流列表、侧边栏等拆分为组件，使首页、推荐结果和其他页面可以复用一致的展示逻辑。

### 91. Vite 在项目中起什么作用？

**参考回答：**

Vite 是前端开发与构建工具，开发阶段利用原生 ES Module 提供快速启动和热更新，生产构建时进行打包与资源优化。本系统使用 Vite 启动 Vue 3 前端，并通过开发代理或 API 配置与 Spring Boot 后端联调。

### 92. 为什么采用前后端分离架构？

**参考回答：**

前后端分离使前端专注交互展示，后端专注业务、算法和数据访问，双方通过稳定接口协作，便于独立开发和测试。代价是需要额外处理接口契约、身份认证、跨域和部署配置一致性。

### 93. 浏览行为为什么使用 `IntersectionObserver` 采集？

**参考回答：**

`IntersectionObserver` 可以由浏览器高效判断帖子是否进入可视区域，比持续监听滚动并反复计算元素位置更节省资源。系统据此记录用户真正看见并停留过的帖子，使浏览行为比单纯页面加载更有意义。

### 94. 如果系统需要支持更大规模用户，应如何优化？

**参考回答：**

首先根据慢查询增加索引和批量查询，并完善分页；其次将热点画像、热门话题和推荐结果放入 Redis 等分布式缓存；再将画像计算、统计聚合和复杂召回转为异步或离线任务。规模继续增长时，还需要消息队列、服务拆分、限流、监控和分布式部署。

### 95. 如何避免 SQL 注入？

**参考回答：**

不要将用户输入直接拼接到 SQL 中，应使用参数绑定、ORM 查询方法或经过校验的查询条件。系统主要使用 Spring Data JPA，由框架完成参数绑定；对于搜索和动态查询，仍需限制输入并避免自行拼接原生 SQL。

### 96. 当前系统有哪些典型的生产化改进点？

**参考回答：**

当前系统适合毕业设计演示，但生产化还需要对密码使用 BCrypt 等哈希算法、启用严格接口授权、收紧 WebSocket 来源、使用 Redis 保存共享缓存、完善数据库索引与并发更新，并增加自动化测试、日志监控、限流和异常告警。
